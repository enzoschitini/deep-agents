# deep_agents

Pacote principal do projeto: um agente de pesquisa construído sobre LangChain **Deep Agents** (`deepagents`), com uma CLI de chat no terminal (rich + prompt-toolkit). Python >= 3.14, dependências gerenciadas com `uv` (`pyproject.toml` na raiz do repo).

## Comandos

```bash
python -m deep_agents.cli          # abre o chat (a partir da raiz do repo); também roda direto via `python deep_agents/cli/__main__.py`
DEEP_AGENTS_DEBUG=1 python -m deep_agents.cli   # erros da CLI com traceback completo
python -m deep_agents.server [--port 8000]      # interface web em http://127.0.0.1:8000 (mesmo agente e mesmas sessões da CLI)
python -m deep_agents.streaming "pergunta" [--level primary|secondary|debug] [--jsonl saida.jsonl]   # despeja os eventos do streaming, um por linha
```

As chaves de API ficam no `.env` da raiz (carregado com `load_dotenv()` em `agent.py` e `harness_profile.py`). Nunca commitar nem ler o `.env` sem necessidade.

## Estrutura

| Pasta/arquivo | Papel |
|---|---|
| `config.py` | Ajustes do agente: `MODEL_CALL_LIMIT` (teto de chamadas ao modelo por resposta, hoje 10; usado em `agent.py` via `ModelCallLimitMiddleware`) e `SUBAGENT_CALL_LIMIT` (teto por tarefa delegada a um subagent, hoje 6; o limite do principal não vale para eles). |
| `bootstrap.py` | Config compartilhada pela CLI e pelo servidor: `MODEL`, `TOOLKIT`, `SUBAGENTS`, `DYNAMIC_SUBAGENTS` e `build_backend(model)` → `Backend(agent, gateway, memory, toolkit, create_agent)`. Mexer em modelo/tools/subagents é aqui, não em `cli/__main__.py`. |
| `server/` | Interface web, só biblioteca padrão. `app.py` (`ThreadingHTTPServer`, serve `frontend/` + API: `GET /api/state`, `POST /api/chat` em SSE, `POST /api/model` (troca o modelo como o `/modello` da CLI: reconstrói o agente, mantém o anterior em caso de erro), `POST /api/session/new`, `/resume`, `/rename`, `/delete` e `/delete_all` (apagam/renomeiam as sessões salvas, as mesmas da CLI); só 127.0.0.1, rejeita `Origin` de outro host; `allow_reuse_address=False` porque no Windows duas instâncias dividiriam a mesma porta), `chat_service.py` (`ChatService`: o equivalente do `ChatCLI._send` sem terminal; um turno por vez; roda o `AgentStreamer` (módulo `streaming/`) numa thread e repassa cada `StreamEvent.to_dict()` como evento SSE (só `visibility` primary/secondary; `debug=true` no POST libera o resto), mais `notice` (falha ao gravar a sessão) e `run/error`; o `run/end` sai por último e leva `answer`, `sources` e `metrics`). A resposta chega em deltas (palavra a palavra) e o frontend a vai montando; as ações aparecem numa árvore de atividades (por `parent_id`), com o botão `Dettagli` (secundárias) e `?debug=1`. Fechar a aba não cancela o turno: ele termina e é gravado na sessão. `frontend/`: `index.html` + `styles.css` + `app.js` + `fonts/` (Inter), tema escuro no estilo da referência `open_bot_design_reference/`, precisa ser aberto pelo servidor (não por `file://`). |
| `agent.py` | `AgentBuilder(config).build()` → `(agent, gateway)` (métodos `build_model`/`build_prompt`/`build_tools`). `dynamic=` (`DYNAMIC_SUBAGENTS` de `cli/__main__.py`: `{"enabled", "max_concurrency"}`) liga os **subagents dinâmicos**: `build_dynamic()` acrescenta o `CodeInterpreterMiddleware(subagents=True)` (tool `eval`, REPL JavaScript, sem `ptc`) aos middlewares, e o principal despacha os subagents registrados com `task()` em `Promise.all`/loops. Só os papéis já registrados (não cria papéis novos); a regra `prompts/rules/09_workflow.md` o restringe a pedidos com a palavra "workflow"; teto de paralelismo em `config.DYNAMIC_MAX_CONCURRENCY`. Os subagents dinâmicos aparecem no streaming como eventos `subagent_dynamic` (início/fim/erro, via canal `custom` do `langchain_quickjs`) sob o evento `code_eval` da tool `eval`; por dentro deles só há esses três eventos (as chamadas ao modelo e as tools internas não passam pelos callbacks). Estudo: `docs/subagents/subagents.md`. Monta `create_deep_agent` com o modelo do gateway, as tools vindas do `ToolkitBuilder` (hoje `internet_search` via Tavily), tudo de prompt vem da fachada `AgentPrompts` (system prompt, regras via `memory=`, skills via `skills=`, backend, permissões). |
| `model/` | Camada de modelos. `ModelConfig` (spec `"provider:modelo"`, temperature, thinking, timeout…), `LLMGateway` (cria o modelo e coleta métricas em `gateway.history`), `ProviderRules` (renomeia/descarta/fixa parâmetros por provedor, ex.: `reasoning_effort` na OpenAI, `thinking` budget na Anthropic), `metrics*.py` (tokens, latência, custo, `tool_runs` plano; a árvore de execução/subagents não é mais daqui: é do `streaming/`). `LLMGateway.tracked_run(label)` entrega `(RunReport, handlers)` e grava `wall_time_s`/`history` ao fim (usado pelo `AgentStreamer`); `run_agent` ficou só como `invoke` (usado por `docs/system_prompt/*`). |
| `prompts/` | `agent_prompts.py` (`AgentPrompts`, fachada usada pelo `agent.py`), `system.py` (`SYSTEM_PROMPT`, `TODAY_PROMPT` com a data de hoje e os textos do perfil do harness), `rules/` (vários `.md` temáticos carregados em ordem alfabética), `skills/<nome>/SKILL.md` (uma pasta por skill, passada em `skills=`; o agente só lê o `SKILL.md` completo sob demanda; hoje: `busca-na-web`), `harness_profile.py` (`HarnessProfiler`, perfil do harness registrado por modelo). A pasta é montada **somente leitura** em `/prompts/`. `workspace.py` (`WorkspaceAccess`): **acesso ao disco real**, só à pasta do pacote `deep_agents/`, montada em `/workspace/` (`FilesystemBackend(virtual_mode=True)`) + `FilesystemPermission` em ordem (primeira que casa vale; sem match = permitido, daí o `deny /**` final): nega segredos (`.*`, `*.key`, `*.pem`) em qualquer lugar, `*.py` e `memory/` só leitura, `/prompts/` só leitura, resto negado. O glob **não casa dotfiles com `**`**, por isso têm regra própria. Sem shell (`execute`), que as permissões não cobrem. O agente é instruído em `rules/07_arquivos.md`. Testes: `tests/test_workspace_permissions.py` (rodar com `uv run --with pytest python -m pytest tests`). |
| `memory/` | Histórico de mensagens de conversas anteriores (uma linha por mensagem: `session_id`, `role` = `human`/`ai`, `content`). `config.py` (ajustes: `SUMMARY_TRIGGER_TOKENS`, `TRIM_TOKENS_TO_SUMMARIZE`, `KEEP_MESSAGES`). `MemoryBuilder` (`build_memory.py`, fachada) tem `summarization()` (`SummarizationMiddleware`: resume o contexto passando de N tokens) e controla a **sessão atual** (`session_id` único por data/hora, `new_session()`, `resume()`, `sessions()`, `history()`, `record_turn()`). A CLI grava as mensagens a cada turno. **O agente não tem tool nem regra de acesso ao histórico salvo** (só o resumo de contexto): sessão nova começa do zero e o passado só entra ao retomar uma sessão com `/sessioni`. `storage/`: `StorageMemory` envolve um backend recebido pronto (o `MemoryBuilder` o escolhe pelo nome: `local_csv` → `data/local_database.csv` (pasta `deep_agents/data/`, ignorada pelo git, junto com `session_titles.json`); `fake_vectorial` → RAM, similaridade fake); todos implementam `MemoryRepository` (definido em `storage_memory.py`, junto com `MemoryRecord` e `SessionInfo`; além de salvar/ler, `delete_session` e `delete_all`). **Nomes das sessões**: `StorageMemory.rename_session` guarda o título num JSON ao lado do CSV (`data/session_titles.json`; no vetorial fake, só em RAM) e `SessionInfo.title` o devolve (vazio = usa a primeira mensagem); `MemoryBuilder.delete_session`/`delete_all_sessions` abrem uma sessão nova se a atual foi apagada. A CLI não tem comando para apagar/renomear, mas `/sessioni` já mostra o nome dado. Os bancos são simulados; a integração com o agente é real. |
| `toolkit/` | Tools do agente. `tools/<tema>.py`: um grupo por tema (subclasse de `ToolGroup` em `tools/base.py`; hoje `tavily.py` → `internet_search`). `ToolkitBuilder` (`build_toolkit.py`) recebe `{grupo: {"enabled", "tools"}}` (definido em `cli/__main__.py`: `TOOLKIT`) e devolve só as tools habilitadas; nome desconhecido é erro. **Dois canais**: o retorno da tool vai ao modelo; o **canal lateral** (`SideChannel`, `side_channel.py`) recebe `publish(toolkit, tool, kind, payload)` (ex.: `kind="sources"` com `{domain,title,url}`) e é lido pelo código com `query(session_id=, toolkit=, tool=, kind=, turn=)` ou `subscribe(cb)`. O canal e o builder são criados uma vez na CLI (sobrevivem ao `/modello`); O `AgentStreamer(channel=...)` chama `begin_turn()` a cada mensagem e, ao fim, emite o evento `sources` (deduplicado por URL, lido do canal com `kind="sources"`), que a CLI desenha no painel `Fonti`; as linhas `⚙ strumento in uso` vêm dos eventos `tool` (resumos por tool em `streaming/actions/labels.py`: `TOOL_SUMMARIES`). Ainda não há consumidor de banco. Grupo novo: criar o arquivo e registrar em `DEFAULT_GROUPS`. |
| `subagents/` | Subagents que o principal chama pela tool `task` (`doc.md` tem as ideias de papéis). `base.py` (`SubagentDef`: `name`, `description`, `system_prompt`, `toolkit` (as tools dele no formato da toolkit, ex.: `{"tavily": {"enabled": True, "tools": ["internet_search"]}}`, independente das tools do principal); `spec(model, tools)` compila um `create_agent` com o modelo do gateway e só essas tools, mais um teto de chamadas), `agents/researcher.py` (`pesquisador`: pesquisa UM ângulo com `internet_search` e devolve até 8 tópicos com fontes + `Lacunas:`), `agents/writer.py` (`redator`: cria um post pronto a partir de notícias da web, com TODAS as tools do grupo `tavily` (`"tools": None`); busca (`topic="news"`), escolhe o ângulo e devolve o post + `Fontes:` (+ `Atenção:` se algo ficou incerto); acionado quando o usuário pede um post com base no que há na internet), `build_subagents.py` (`SubagentBuilder(config)`: `{subagent: {"enabled"}}`, definido em `cli/__main__.py` como `SUBAGENTS`; `AgentBuilder.build_subagents()` entrega o modelo e o `ToolkitBuilder` do agente, de onde o subagent tira só os grupos de tools e o canal lateral; subagent, grupo ou tool desconhecido é erro). A regra `prompts/rules/08_subagentes.md` diz ao principal quando delegar: `pesquisador` com 3+ ângulos independentes (uma `task` por ângulo, todas na mesma rodada); `redator` em pedidos de post (uma `task`, e o principal entrega o post inteiro, sem resumir: o perfil do harness manda responder em 3 frases, e a regra o afasta disso para o conteúdo do post). Os dois usam o grupo `tavily` da toolkit com o mesmo canal lateral, então `internet_search` publica as fontes no mesmo canal lateral (painel `Fonti`). **Por que `CompiledSubAgent` e não o dict `system_prompt=`/`tools=`**: o `HarnessProfile` do modelo vale também para subagents declarativos e o `base_system_prompt` dele SUBSTITUI o `system_prompt` deles (o `system_prompt_suffix` é anexado: o "3 frases" do perfil cortaria o pesquisador). Compilado, fica fora do perfil. Subagent novo: criar o arquivo e registrar em `DEFAULT_SUBAGENTS`. |
| `streaming/` | **Streaming da resposta e das ações** (substitui o antigo `on_event`/`_LiveSteps`/árvore do `MetricsCallbackHandler`). `AgentStreamer(agent, gateway, options=, channel=).start(messages)` → `RunHandle` (iterável de `StreamEvent`, `cancel()`, `join()`, `.result` = `RunResult`: state, answer, report, stats, error, cancelled, sources); também `stream()` e `astream()`. Roda numa thread `agent.stream(stream_mode=["messages","updates","custom","values"], subgraphs=True, version="v2")` e combina: tokens (`messages`), callbacks (`ActionCallbackHandler`: ciclo de vida de LLM e tools com run_id/tool_call_id/duração/usage/erro), `updates` (fim de mensagem, interrupts) e `custom` (subagents dinâmicos, `get_stream_writer`). `events.py`: `StreamEvent` JSON-serializável (`kind`, `phase` start/delta/end/error/info/cancelled, `id`/`parent_id`/`agent`/`agent_id`/`ns`/`depth`, `label` pronto em italiano, `args`, `summary`, `duration_s`, `visibility` primary/secondary/debug, `data`); tipos: run, response, reasoning, model_call, tool, tool_args, subagent, subagent_dynamic, code_eval, async_task, todos, skill, file, summarization, graph_step, sources, custom, interrupt, notice. O módulo emite TUDO; o front filtra por `visibility`. `response/` (`ResponseStreamer`: deltas palavra a palavra ou por token, reasoning, `RESPONSE/END` com `data.final`: `False` = texto intermediário antes de uma tool; descarta tokens de subagent e de chamadas de resumo) e `actions/` (`ActionTracker`/`ActionCallbackHandler`, `classifier`, `labels`, `stream_parser`, `summarize`). `bus.py` (`EventBus`: `seq`, fila, sinks), `registry.py` (`RunRegistry`: liga namespace do LangGraph ↔ `task` ↔ subagent), `options.py` (`StreamOptions`, instância `STREAMING` em `bootstrap.py`), `adapters/` (`ListSink`, `JsonlSink`, `CallbackSink`, `visibility_filter`, `encode_sse`). A resposta final oficial é `RUN/END.data.answer` (os deltas são provisórios). Sem `stream_events(version="v3")` (experimental). |
| `cli/` | `ChatCLI` (`app.py`, ciclo e comandos; `/dettagli [off\|on\|debug]` liga as ações secundárias/debug), `Renderer` (`renderer.py`, tudo o que se desenha) + `LiveTurn` (`live_turn.py`, consome os eventos do streaming: status enquanto pensa, linhas das ações, resposta em `Live` Markdown; só o `Renderer` o instancia), `commands.py` (registry de comandos `/…`), `models.py` (lista/escolha de modelos), `prompt.py`, `banner.py`, `theme.py` (cores). |
| `utils/json_manager.py` | `manage_result_json`: salva o resultado completo do agente em `data/agent_result.json`. |
| `docs/` | Material de estudo (prompts isolados `docs/system_prompt/01..06`, mapa da doc). Não faz parte do runtime. |

## Fluxo

`cli/__main__.py` define `MODEL_SPEC`/`MODEL`, cria um `MemoryBuilder` e a fábrica `create_agent` (`AgentBuilder(config, memory=memory).build()`) → `ChatCLI(agent, gateway, agent_factory=create_agent, memory=memory).run()`. Trocar modelo/temperatura/thinking no chat chama `agent_factory` de novo (a conversa continua; em caso de erro mantém a configuração anterior).

**Histórico enviado ao agente**: o agente é chamado sem checkpointer, então a CLI reenvia a conversa a cada turno, **só como texto** (`{"role": "user"/"assistant", "content"}`; `ChatCLI._remember`), sem as chamadas e resultados das tools. Nunca voltar a `self.messages = result["messages"]`: carrega os resultados brutos das buscas em todo turno seguinte e, como o `_summarization_event` do resumo de contexto é estado privado que não sobrevive entre chamadas, refaz o resumo do histórico inteiro a cada pergunta (até para um "valeu": 2 chamadas, ~24 mil tokens). O resumo agora dispara por **tokens** (`SUMMARY_TRIGGER_TOKENS`), não por nº de mensagens (que disparava no meio da pesquisa). A data de hoje entra no system prompt (`TODAY_PROMPT`), para o agente não pesquisar a data na web. O `[extra_middleware]` recomeça a contar a cada pergunta; o nº entre parênteses é a contagem bruta do estado, não o que vai ao modelo.

**Streaming no terminal e na web**: `ChatCLI._send` e `ChatService._run` iniciam um `AgentStreamer` e consomem os `StreamEvent`. Subagents (`task`) vêm como eventos `subagent` e as tools/chamadas ao modelo deles chegam com `parent_id` = tool_call_id da `task` (a CLI as indenta sob `◈ subagent`). A linha de métricas usa `format_metrics(report, stats)` (`stats` = `RunStats` do `RUN/END`). Ctrl+C na CLI chama `handle.cancel()`: só interrompe entre chunks (não mata a chamada em curso ao LLM); na web fechar a aba não cancela o turno.

**Sessões**: cada execução da CLI começa uma sessão nova e vazia; o banner mostra o ID e o nº de mensagens. `/pulisci` abre outra sessão nova (a anterior continua salva) e `/sessioni` lista as salvas num seletor; escolher uma carrega o histórico como contexto e a conversa continua nela (`/sessioni <id>` retoma direto). Sem `memory=`, essas funções ficam desligadas.

## Convenções

- **Idiomas misturados de propósito**: textos da interface da CLI (mensagens, comandos `/aiuto`, `/modello`…) em **italiano**; comentários e docstrings em **português**; nomes de código em inglês. Manter isso ao editar.
- Imports no topo dos entry points usam `# noqa: E402` porque o `sys.path` é ajustado antes (permite rodar com o botão Play). Não "arrumar".
- Todo desenho no terminal passa pelo `Renderer`; `ChatCLI` não imprime direto. Erros: `view.error(e, contexto)` — sempre passar o contexto (onde falhou).
- Parâmetros específicos de provedor pertencem a `ProviderRules`, não ao `LLMGateway` nem à CLI. Para suportar um provedor/modelo novo, estender `DEFAULT_RULES`.
- O agente só acessa `/workspace/` (pasta `deep_agents/`) e não escreve em `/prompts/**`, `*.py` nem `memory/` (permissões `deny`); mudanças em `prompts/rules/*.md` são feitas por você no disco.
- `HarnessProfiler.register(spec)` precisa rodar para cada modelo (inclusive após `/modello`); chaves com nome errado em `tool_description_overrides` viram no-op silencioso.
- Testes do streaming: `tests/test_streaming_*.py`, `test_cli_live.py`, `test_chat_service_stream.py`, `test_gateway_tracked_run.py`; `tests/fakes_stream.py` tem `StreamingScriptedChat` (emite tokens, p/ rodar o agente real offline com streaming). Os testes antigos `test_agent_session`/`test_cli_history`/`test_subagents` (apagados num commit anterior) não foram restaurados.
- Testes ficam em `tests/` na raiz do repo (`LLMGateway` aceita `model=` para injetar um modelo fake; `tests/test_subagents.py` cobre o pesquisador com um modelo que decide pela situação, não por roteiro, porque dois subagents rodam em paralelo e disputariam um roteiro único). Rodar: `uv run --with pytest python -m pytest tests`. `tests/fakes.py` tem um modelo com roteiro (`ScriptedChat`) que faz o agente REAL (create_deep_agent + middlewares) rodar offline e registra cada chamada, inclusive as de resumo; `test_agent_session.py` usa isso para garantir que uma sessão de pesquisa não faz chamadas escondidas. Testes que usam `MemoryBuilder` devem passar `database="fake_vectorial"` (em RAM) para não escrever no `local_database.csv` real.
